# Agent 工作与收敛契约

## 责任与范围

本契约管理开发助手的行动选择、验收和汇报，不改变研究引擎、评分、PIT、
Signal 准入或业务 canonical records。2026-10-19 用户授权依据复盘重构项目 meta。
研究设计仍遵循 [vision](vision.md) → [architecture](architecture.md) → owning spec。

用户决定目标、研究定义、优先级和资源边界；助手负责查明事实、设计诊断、
实现、验证和维护简短续接状态。真实入口、适用错误家族、恢复与后继消费的
核验是助手责任，不能依赖用户反复提醒。已有授权持续有效；普通实施选择自主
完成。只有超出授权或改变上述设计边界的实质取舍才请求决策，并先准备具体方案。

## 一个批次解决一个验收问题

多步骤工作开始时，在对话中简述：目标验收项及证据层、当前失败证据、待区分的
解释、最小检查与停止条件。结束时只需回答：关闭了什么、依据是什么、还缺什么、
下一步是否值得做。不按调用/提交/测试/报告/版本数量衡量进度。

选择能改变判断的检查：预先说明什么观察支持当前解释、什么观察反驳它，
两种结果分别采取什么动作。若只是无条件继续原样运行，重新设计检查；两种结果
都停止也可以合理，但须说明各自结论。先做能区分原因的最小诊断；完整运行须
说明它为什么不能被更小的检查替代。按风险验证，普通低风险编辑无需假说表、
新 ledger、独立评审或付费实验。

分别证明以下事项，不能由其中一项代替其他项：

| 事项 | 所需证据 | 常见误代 |
| --- | --- | --- |
| 输入可信 | 历史正文版本、来源时间、对象/期间/单位 | hash、可解析日期 |
| 执行正确 | 真实入口、生产数据形状、持久化/恢复 | 局部 fixture、exit0 |
| 反馈正确且消费 | 原证据→诊断→实际后继输入→行动 | 反思文本、引用、采纳字段 |
| 新能力及复用 | 准入、发布、精确版本实际执行 | candidate、Registry 数量 |
| 独立收益 | 批准的可比独立评价、完整失败分母 | 同案正确、置信度、单次 F1 |

诊断降低不确定性、局部修复和目标完成分别汇报。证据阶段可以是 diagnosed、
local、live、independent；只有达到命名问题要求的证据才 closed。阶段是该问题
内部的标记，不使独立评分自动证明输入或反馈正确。诚实 no_gain/no_pattern 有效；
有限搜索不能证明模式不存在。可靠且可比的独立评价持续无增益时，回到研究假设，
不无限添加工程机制，也不强制产生因子或类别配额。

## 复发时改变行动

以下任一情况触发本契约及 [经验索引](../memory/GUIDE.md) 的相关条目：
同类失败复发或迁移、连续两轮无目标验收推进、输入/合同/修复权限矛盾、
声明超过证据，以及准备完整付费后继或增加机制/范围。持续工作约 30 分钟
仍在修补或扫描时检查信息增量；可以在对话中完成，不制造定时记录。

1. 先区分真正回归、同族漏修、修复未进入运行、过早关闭或尚未知；绑定实际
   run/revision/输入和权威指针，不能笼统称“模型又犯错”。
2. 找到首次信息丢失/误解处，沿适用链检查 producer→prompt/input→validator
   →typed repair→fallback→consumer→persistence/recovery→next-cycle。
   逐项明确适用范围，不要求无关路径陪跑。检查合同本身是否可满足、语义是否正确。
3. 解释旧检查为何漏过、助手遗漏了什么。给出原失败、代表性变体、反例和适用的
   后继证据；测试必须经过被验收的真实连接，不 mock 掉它。尽可能证明新检查
   能在旧缺陷上失败。语义验收须回到原材料，不能只让实现与测试互相印证。
4. 选择下一动作：有边界诊断、修复错误家族、完整后继、停止策略或请求实质决策。
   两轮无目标推进时，说明新增诊断排除了什么；没有新增信息就换假设/范围或停下。
   保持同一策略须有新证据和区分变量。改策略名、清空历史、换目标都不算改变。

重要关闭结论及复发修复使用反例审查：优先由只读审查者查看原始证据、实际连接和
声明边界；无独立审查者时明确做自审及其局限。无需为普通改动拆 agent，多个
agent 赞同不构成独立研究收益。审查不替代实际验收。

## 简明记录与行动检查（meta schema 2）

长期研究使用已有 [convergence.json](../progress/convergence.json)，只在实质
轮次/复盘/决策边界更新。普通编辑只同步 status/changelog；本次 meta 重构不能
伪造研究 iteration、升级研究 acceptance、刷新历史 goal receipt 或移除未满足前提。

`acceptance`、`iterations`、`goal_snapshot`、`successor_prerequisites` 和历史归档
沿用已有字段。`acceptance_advances` 表示达到该项要求的验收证据，诊断信息写在
review，不伪装为目标完成。最新轮次 advance 的层级不得超过该 acceptance 的当前
level；旧历史不重写。最近两轮都无 advance 即需当前 review，不依赖 strategy 名。

需要 review 时，它必须对应最新 iteration，有可访问证据和 missed assumptions。
`review.decision` 使用以下字段，后继只引用它，不重复一份实验说明：

- `acceptance_id`：本批主验收项，必须存在；继续工作须未关闭。stop 可引用已关闭项
  以记录停止工作，不要求重开已完成问题。
- `kind`：`diagnose | repair | full_successor | stop | human_decision`。最后一种仅表示
  需要用户做实质取舍，不自动增加审批；stop 不自行修改目标服务状态。
- `strategy`、`action`、`stop`：方法、具体行动、资源/重复无信息/前提失败的停止条件。
  同策略续行仍需 `new_evidence` 与 `distinguishing_variable`；stop/human_decision
  不属于续行，不要求编造新实验或新证据。
- diagnose/repair/full_successor 另需 `question`、`pass`、`fail`、`on_pass`、`on_fail`：
  要区分的问题、可观察的支持/反驳结果，以及各自下一步。语义区分由审查负责，
  不用两个字符串不等冒充有效诊断。停止/请求决策不必编造一个实验。

完整付费后继前刷新运行终态、目标服务及用户答复，满足原授权/预算与前提，
冻结 revision/manifest/合同，运行 `python3 scripts/check_project.py --before-successor`。
除已有检查外，必须 `decision.kind=full_successor`；`successor_plan` 的 `strategy`
和 `acceptance_id` 与该决策一致，并有 `why_full_run` 和 `budget`，分别说明完整
运行的必要性和授权证据中给定的资源上限。保留 `authorization_evidence`、
`freeze_evidence`、40 位 `revision`、64 位 `manifest_sha256`；删除重复的
question/pass/fail/stop。诊断或停止决策不能靠填同名 strategy 放行完整运行。

目标 receipt 仍须为 10 分钟内的 active，null/过期/usageLimited/budgetLimited
不能允许启动或借新目标绕过。单独授权的工作保持独立范围。缺前提先处理前提，
不改记录求 PASS。行政检查只读本地记录，不访问服务、不执行或授权业务运行。

checker 可拒绝缺字段、引用不一致、动作类型冲突；不能识别换句话说的同一策略、
验证文件里的证据真假、预算授权真实性或判断经济语义。它也未接管 executor。
助手仍负责实际决策和语义审查，不得把字段完整/PASS 当作学习或收益证明。

## 维护与验收

AGENTS 保持短入口，status 仅当前事实、限制和下一步；历史有明确日期。经验只在
匹配触发时读；不计数、不写咨询日志、不作 bookkeeping-only 提交。重复规则改为
指向本契约；无效规则应缩小范围、转机械检查或删除，不能无限叠加提醒。

脚本反例使用独立构造的小型记录，不能从真实账本复制后仅将路径换成通用 proof。
另从实际 CLI 经过读取→验证→退出码验证拒绝和允许路径，保留真实仓库一致性检查。
对比旧检查确认关键反例原先可通过；检查通过只关闭本地行政缺陷。
首次真实业务触发仍须确认是否改变行动并获得区分信息；未发生则保留待验证。

实施完成后同步相关 spec、status 和一条有意义 changelog，运行适当测试及
`scripts/lint_repo.sh`，读取 `.lint-feedback/pre-push-last.log`。检查 git status，
只提交本任务文件；保留其他改动。无需为此创建新报告体系或变更业务状态。
