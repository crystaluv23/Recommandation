# Agent 工作与收敛契约

## 范围与权限

本契约管理开发助手如何选择工作、复盘、验收和汇报；不改变股票研究引擎、
评分、标签、PIT 定义、Signal 准入或 canonical records。2026-10-07 用户授权
重构项目 meta 机制。研究框架仍受 [vision](vision.md) 与
[architecture](architecture.md) 约束；业务模块变更仍先读其祖先和模块 spec。

AGENTS.md 是必读入口。本契约按触发读取；经验是有适用范围的证据，不是更高权限。
既有用户授权持续有效。反思触发不自动产生审批；只有改变研究定义、接口、
canonical schema、PIT 保证、评分或外部行动范围时才需要对应人类决策。

## 工作单位与进展

长任务以一个有边界的工作批次推进。开始前说明：要关闭的具体问题、当前失败
证据、最有区分力的假设、验证方式、停止条件。多步骤工作给出可核验成功标准。
普通低风险编辑不需要新增 ledger 或复盘文件。

分别记录以下证据层，不能用下一行的数量冒充前一行的质量：

| 层 | 可接受证据 | 不能替代它的材料 |
| --- | --- | --- |
| 输入可信 | 历史正文版本、来源时间、对象/期间/单位适用性 | hash 相等、日期可解析、URL 看似合理 |
| 执行正确 | 真实入口、完整合同、持久化和恢复 | exit0、局部测试、临时结果 |
| 反馈正确且消费 | 原证据到教训到后继实际 payload/行为 | 写出反思、采纳字段、引用存在 |
| 新能力及复用 | 准入、原子发布、精确版本执行/引用 | candidate、旧 fixture PASS、Registry 数量 |
| 独立收益 | 已批准且可比的独立评估、完整失败分母 | 同案正确、置信度、F1 单次变化 |

每轮结尾必须能回答“哪一项验收向前移动、证据是什么、还有什么未关闭”。
无推进可以如实记录。诊断、局部修复和覆盖扩展可以有价值，但必须说明它们
降低了哪项不确定性；测试数量、报告数量、提交数量和运行版本号不是验收进展。
问题按所需证据标记 diagnosed / local_verified / live_verified / closed。
只有达到该问题预先声明的验收层级才 closed；不强迫所有工程问题都做付费实验。

## 必须触发系统反思的情形

任一条件出现，先处理反思，再继续同类高成本工作：

1. 被称为已修复的问题家族再次发生，或者同一根因跨相邻阶段迁移。
2. 连续两轮使用相同工作策略，没有推进任何目标验收项。
3. 输入可信性、合同、修复权限或反馈归因出现矛盾，原实验前提失效。
4. 局部 PASS 被用来支持 live / 学习 / 收益等更高层结论。
5. 准备启动完整付费后继、增加机制复杂度或扩大实验范围。
6. 持续工作约 30 分钟仍只在修补或扫描：检查当前工作是否仍有信息增量。

计时检查可留在对话中；只有改变了决策才更新复盘。不要定时制造文档。
goal 或预算限制是控制信号，优先于任何复盘或持久工作要求。

## 反思必须改变行动

阅读累计失败轨迹和相关旧经验，回答以下问题：

- 这次问题与以前哪类问题相同？为什么旧检查和旧教训未阻止它？
- 沿 producer → prompt/input → validator → typed repair → fallback → consumer
  → persistence/recovery → next-cycle 追踪，哪个边界首次丢失或错误解释信息？
- 合同本身是否错误或不可满足？结构一致性是否正在保存错误研究语义？
- 我执行时忽略了什么：真实生产构造、模型可见内容、未用能力、反馈原因、
  数据历史版本、对照、冻结版本，还是验收标准？避免笼统归咎模型。
- 哪些仍是未知，哪些有反例？旧答脚本回放究竟证明兼容性还是新行为？
- 下一步为什么比重复上一轮更有信息量？什么结果会推翻当前判断？

复盘结论必须选择一个具体动作：修复整个适用错误家族、缩小到能区分根因的
诊断、补齐输入前提、转向另一假设，或停止当前策略。记录通过/失败判据和停止
条件。单纯“继续加强 prompt / 更多测试 / 再跑一轮”不构成策略变化。
确需保持同一策略时，说明新证据为何使原假设仍成立，以及本次不同的区分变量。

禁止用强制因子/类别配额、削弱 validator、删除失败分母或机械代写经济判断
制造收敛。诚实 no_pattern 合法；有限搜索也不证明因子不存在。

## 完整后继前的行政检查

长期收敛任务的简明记录放在 [convergence.json](../progress/convergence.json)。
只在一轮结束、触发复盘、证据层改变或决定下一次完整后继时更新，不记录每次
调用。iterations 记录策略、失败家族、真正推进的验收项及依据；review 覆盖
最新轮次并记录自身盲点、改变的动作和判据。未知值保留未知。

启动新的完整 Fast/Slow 或其它完整付费后继前，助手必须：

1. 刷新目标服务状态和运行终态，不以旧 PID/日志推断活跃；核对最新用户答复。
2. 更新本次拟验证的问题、冻结 revision / manifest / 合同、授权与预算依据。
3. 运行 `python3 scripts/check_project.py --before-successor`；任何未满足的前提
   先处理，不启动重复完整运行。针对诊断的已有授权可继续，不能将诊断说成完整验收。

checker 检查 meta 记录和上述最低前提；不接管业务 executor、不访问网络、不
自动调用模型、不验证市场研究真假，也不能授予权限。其 PASS 是行政准备，
仍需真实生产验证。未通过时报告具体原因，不能通过改记录替代证据。
快照只允许 10 分钟内的新鲜 active 状态支持启动；null 不等于 active。
usageLimited / budgetLimited 不允许继续该目标、替换目标或自行改状态。
若用户另行授权独立工作，按该工作范围进行，不借此恢复受限目标。

## 经验、状态与规则本身的复审

- 查阅经验无需计数、日志或提交。采用/不适用/反例只在改变决策时附一句依据。
- 经验反复无效、与合同冲突或只增加维护成本时，修订范围、转成机械守卫、
  合并或淘汰；“读过很多次”不是有效性证明。
- [status](../progress/status.md) 只保留当前结论、限制、证据入口和下一步；
  历史留在 changelog/reports/归档，旧 ACTIVE 标明历史。
- 实施后的首次适用事件检查本机制是否真正触发了不同决策。没有实际效果时
  继续修 meta；不能用本契约、checker PASS 或更多记录宣称系统已收敛。
- 不得为绕过停滞触发而重命名策略/问题家族、清空轮次或重建目标。

## 维护与验证

`scripts/check_project.py` 仅检查 meta 契约、证据路径、停滞/复发复盘及后继前提。
`tests/test_project_meta.py` 使用独立临时 ledger 验证反例，不修改真实研究状态。
repo lint 调用默认检查；`--before-successor` 是助手启动前的显式硬门槛。
保存历史状态原始字节及 hash，验证短入口能到达原始报告。按任务范围提交，
不提交用户无关改动。研究 runtime 的端到端验收依旧单列。
