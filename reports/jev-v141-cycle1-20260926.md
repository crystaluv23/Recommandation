## New structural limit found at cycle 2

`external_request_token_budget_exhausted`: the Information Plan proposal
required a conservative reservation of 403,119 against the frozen per-request
limit of 256,000 (h1 budget 512k), because cycle 1's committed history now includes
both candidates' full 24-case rounds. Retrying cannot help — the context grows
with every committed round. The run paused cleanly (workspace consistent,
cycle 1 committed, no processes left).

2026-09-28 measurement correction: `estimate_json_request_tokens` reserves the
serialized HTTP request's UTF-8 byte count plus the maximum output-token limit.
403,119 is therefore not a tokenizer-measured input-token count. This was a local
preflight rejection; it does not establish a provider context-window overflow.

The persisted proposal-start event contains just two meta entries (`[-1, 1]`)
with 72 case reflections (24 imported, 48 local). An offline reconstruction from
the frozen artifacts puts meta at approximately 333 KB, or 95% of the user JSON
payload; the two parent Plans contribute approximately 15 KB. The reconstructed
HTTP body is 367,115 bytes plus a 36,000 output allowance, four units below the
recorded reservation; next-round alias masking was not fully reconstructed, so
this is a composition measurement rather than byte-exact replay or sent usage.

Options for the user (design decision, not improvised here):

1. Raise the proposer's frozen `limits.max_tokens` through a fresh contract
   (only defers the budget limit as history grows). The earlier suggestion to
   raise `--h1-request-budget` was incorrect for this failure: that setting
   configures Mining, while the proposer takes `limits.max_tokens`.
2. Bound/compact the proposal history (e.g., parent-only case summaries
   instead of full round history) — an architecture change in the proposal
   context builder.
3. Keep cycles at one and treat each cycle as a fresh freeze (loses
   cross-cycle learning accumulation in the fast loop).
